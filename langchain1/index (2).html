Welcome to the GenAI Security Lab

This hands-on lab environment lets you explore real AI security attacks and defenses using a local AI model via Ollama. No API key required. Follow the setup steps below, then select a lab module from the sidebar.

Setup Instructions

Complete these steps once before starting any lab. Estimated time: 5–10 minutes.

1

Install Ollama

Ollama runs AI models locally on your machine — no API key or internet connection required after install.

macOS

Option A — Direct download (recommended):

  1. Go to ollama.com/download
  2. Click Download for Mac
  3. Open the downloaded Ollama.dmg and drag to Applications
  4. Launch Ollama from Applications — the menu bar icon confirms it's running

Option B — Homebrew:

brew install ollama
Windows
  1. Go to ollama.com/download
  2. Click Download for Windows
  3. Run the installer OllamaSetup.exe
  4. Ollama starts automatically and appears in the system tray
Linux

Run this single command in your terminal:

curl -fsSL https://ollama.com/install.sh | sh
2

Download the Llama 3.2 Model

Open a terminal and run the following command. This downloads the Llama 3.2 model (~2 GB) to your machine.

ollama pull llama3.2

Download takes 2–5 minutes depending on your connection. You'll see a progress bar in the terminal.

System requirements: 8 GB RAM minimum (16 GB recommended). Works on Mac (Apple Silicon or Intel), Windows 10+, and Linux. GPU optional — runs fine on CPU.

3

Start Ollama with Lab Access Enabled

The lab runs in your browser and needs permission to call the local Ollama API. Start Ollama with cross-origin access enabled:

macOS / Linux
OLLAMA_ORIGINS=* ollama serve
Windows (Command Prompt)
set OLLAMA_ORIGINS=* && ollama serve
Windows (PowerShell)
$env:OLLAMA_ORIGINS="*"; ollama serve

Keep this terminal open while using the lab. You should see: Listening on 127.0.0.1:11434

⚠ Getting address already in use?

Good news: the server is already running and healthy — it is only refusing this page. On macOS and Windows alike, something supervises that server and restarts it the moment it dies, which is why a fresh PID appears after every kill and why ollama serve then cannot claim the port. Killing it can never work. Set the variable first, then restart the supervisor — in that order.

macOS — step 1: find out what is supervising it
brew services list ls ~/Library/LaunchAgents ps -o pid,ppid,command -p $(lsof -ti :11434)

If ollama is listed by brew services list, you have the Homebrew service — use 2a. If the parent process is the Ollama application, you have the desktop app — use 2b. Installed with brew install ollama? Then there is no application bundle and no menu-bar icon at all. That is expected, not a broken install, and 2a is your route.

macOS — step 2a: Homebrew service
launchctl setenv OLLAMA_ORIGINS "*" brew services restart ollama

Both lines, in that order. launchctl setenv only reaches processes launched after it runs, so the restart is what actually applies it — setting the variable on its own changes nothing. Prefer a terminal you control? Run brew services stop ollama first, then OLLAMA_ORIGINS=* ollama serve.

Heads-up: launchctl setenv only lasts for the current login session. After a reboot the service starts again without the variable and the lab goes back to amber, so you would repeat these two lines every time. The block below makes it permanent.

macOS — step 2b: desktop app
launchctl setenv OLLAMA_ORIGINS "*"

Then click the llama icon in the menu bar → Quit Ollama and relaunch it. Quitting is the part that matters: the variable never reaches a server that is already running. This lasts until you restart the Mac — see Making it stick across reboots below.

Linux
sudo systemctl stop ollama OLLAMA_ORIGINS=* ollama serve

The packaged install runs under systemd, so stop that service before starting your own.

Windows — the permanent fix (recommended):

On Windows the auto-started tray app serves the browser, so a session variable (set / $env:) never reaches it. Set the permission permanently and restart the app:

1. Quit the tray app — find the llama icon in the system tray (you may need the ^ arrow), right-click → Quit Ollama.

setx OLLAMA_ORIGINS "*"

2. You should see SUCCESS: Specified value was saved. — unlike set, setx makes it permanent.

3. Relaunch Ollama from the Start menu, then refresh this page.

Or run the server manually instead (PowerShell):
Get-Process -Name "ollama*" | Stop-Process -Force $env:OLLAMA_ORIGINS="*"; ollama serve

Quit the tray app first — otherwise the browser keeps talking to the already-running tray app, which never got the variable.

macOS — making it stick across reboots

launchctl setenv is session-scoped, not permanent: a restart wipes it, the Homebrew agent brings Ollama back up without it, and the lab returns to amber. The cleanest permanent fix is a launch agent of your own that carries the variable with it. Do not edit homebrew.mxcl.ollama.plist — brew services regenerates that file every time it starts, so your edit disappears.

brew services stop ollama which ollama  # note the path, usually /opt/homebrew/bin/ollama

Then create ~/Library/LaunchAgents/com.local.ollama.plist with this content, replacing the path on the <string> line if which reported a different one:

<?xml version="1.0" encoding="UTF-8"?> <!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN" "http://www.apple.com/DTDs/PropertyList-1.0.dtd"> <plist version="1.0"> <dict> <key>Label</key><string>com.local.ollama</string> <key>ProgramArguments</key> <array> <string>/opt/homebrew/bin/ollama</string> <string>serve</string> </array> <key>EnvironmentVariables</key> <dict> <key>OLLAMA_ORIGINS</key><string>*</string> </dict> <key>RunAtLoad</key><true/> <key>KeepAlive</key><true/> </dict> </plist>

Load it once — it starts on its own at every login from then on:

launchctl bootstrap gui/$(id -u) ~/Library/LaunchAgents/com.local.ollama.plist

To undo it later: launchctl bootout gui/$(id -u)/com.local.ollama, delete the plist, then brew services start ollama.

Still stuck on any OS? Serve the lab instead of opening the file

Opening index.html by double-click makes the browser report this page's origin as null, which Ollama rejects unless OLLAMA_ORIGINS is set. Serving the same file over localhost avoids the problem entirely, because Ollama trusts http://localhost on any port by default — no variable, and nothing to restart. In the folder that holds index.html:

python3 -m http.server 8000

Leave that window open and visit http://localhost:8000/index.html. Your existing Ollama server stays exactly as it is.

No python3? Recent macOS versions no longer bundle it, so the command may just offer to install Apple's developer tools. Either accept that, or open the folder in VS Code and use the Live Server extension — its 127.0.0.1:5500 is trusted by Ollama out of the box too.

4

Verify the Connection

Once Ollama is running, verify it's reachable by opening a new terminal and running:

curl http://localhost:11434/api/tags

You should see a JSON response listing llama3.2 in the models list.

Then check the connection indicator in the top-right corner of this page — it should turn green.

The command works but the dot stays amber? That is a CORS block, not a dead server — curl ignores CORS, your browser does not. The lab says so explicitly: amber reads Ollama running — but blocking this page, and clicking that status text jumps you to the fix for your OS in Step 3 above. Do not kill the server; it is working. To confirm the diagnosis, press F12 → Console and refresh — a red CORS error means the variable has not reached the running server.
